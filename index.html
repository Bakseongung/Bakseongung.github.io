핵심주요보조

  • AWS의 Auto Scaling Group처럼 부하에 따라 VM이 자동으로 늘어나는 구조를,
    OpenStack의 클러스터링 서비스(Senlin) 없이 Heat 오케스트레이션만으로 직접 구현한 프로젝트입니다.
  • ZeroTier 오버레이망 위에 OpenStack·Docker Swarm·HAProxy를 구성하고,
    Prometheus 알림부터 Ansible·Cloud-init으로 VM 생성과 Swarm 편입까지 자동화했습니다.
  • 팀장 겸 PM으로 프로젝트를 총괄하며 인프라 아키텍처를 설계하고 Flask 관리자 페이지를 개발했습니다.
  • 부하가 있을 때만 VM을 늘리는 오토스케일링과 Cooldown으로 중복 VM 생성을 막아 자원 낭비를 줄였고,
    별도 클러스터링 서비스 없이 Heat와 오픈소스(Prometheus·Grafana·MinIO)만으로 구성했습니다.

트러블슈팅

  • 악성코드 감염 및 보안 구조 개선 문제운영 중 Control 서버와 Vault 서버에서 Diicot 계열 크립토마이너/백도어를 발견했고,
    비정상 프로세스 실행과 외부 의심 통신을 확인     원인초기 운영 환경에 접근 제어와 Secret 관리 체계가 부족했음 해결감염 노드를 ZeroTier에서 격리하고 SSH Key·Token을 교체, HashiCorp Vault로 Secret을 중앙 관리, UFW·Fail2ban·ModSecurity·Auditd로 보안 체계 강화 추가 확산 방지, 민감정보 관리 구조 개선
  • NFS 기반 공유 스토리지 구성 문제 문제Docker Swarm에서 Worker Node별 로컬 스토리지를 쓰다 보니,
    컨테이너가 다른 노드로 옮겨가면 기존 데이터에 접근할 수 없고 노드별 데이터가 어긋남     원인Docker Swarm은 컨테이너 배치는 자동화하지만 로컬 볼륨 데이터 동기화는 지원하지 않음 해결중앙 Storage 서버에 NFS를 구성해 Worker Node에 공유 볼륨으로 마운트하고,
    Docker Volume Driver를 NFS 기반으로 변경한 후 저장 데이터는 MinIO로 백업     모든 Worker Node가 같은 데이터에 접근, 컨테이너 이동 시에도 데이터 유지
  • 모니터링 메트릭 수집 누락 문제Grafana 대시보드에 새로 생긴 노드의 CPU·Memory 메트릭이 표시되지 않음 원인Prometheus는 미리 등록된 Target에서만 Pull 방식으로 수집한 후,
    오토스케일링으로 생긴 VM 정보가 Target에 자동 반영되지 않음     해결VM 생성 파이프라인에 모니터링 등록 단계를 추가하고,
    Node Exporter 상태 확인 후 Prometheus Target 설정을 자동 업데이트     Scale-Out 이후에도 신규 VM 메트릭을 실시간 수집
  • Auto Scaling VM 자동 편입 문제 문제OpenStack에서 VM 생성은 성공했지만,
    새 VM이 ZeroTier와 Docker Swarm 클러스터에 자동으로 편입되지 않음     원인ZeroTier 노드 승인 절차가 필요하고 Cloud-init 실행 순서와 Swarm Join 시점이 맞지 않음 해결VM 초기화 파이프라인을 다시 설계해 Cloud-init으로 네트워크 설정을 자동화하고,
    Swarm Worker Join 자동화와 재시도 로직 추가     VM 생성부터 서비스 클러스터 편입까지 자동화
  • Auto Scaling 안정화 문제 문제CPU Threshold를 넘으면 Alert가 여러 번 발생해 VM이 중복 생성됨 원인Scale 이벤트 상태 관리와 Cooldown 로직이 없었음 해결현재 인스턴스 상태 확인 로직을 추가하고 Cooldown Time을 적용해 중복 Scale 이벤트 방지 불필요한 VM 생성 없이 안정적인 Scale-Out

아쉬운 점

  • 서비스 운영 보안 강화 필요 인프라 보안 체계는 갖췄지만 실제 서비스 운영 관점의 계정·Secret 관리 정책과 IAM 기반 권한·인증 체계는 보완이 필요함
  • ZeroTier 기반 네트워크 성능 한계 오버레이 네트워크 특성상 물리 네트워크보다 지연이 생길 수 있으므로,
    대규모 트래픽에서는 전용 네트워크나 최적화된 VPN 구조 검토가 필요함
  • Auto Scale-In 미구현 트래픽 증가에 대응하는 Scale-Out 중심으로 구현했고, 축소(Scale-In)는 기간이 더 필요했음
  • 서비스 플랫폼 확장성 한계 실제 사용자 서비스를 위해서는 Backend·Database 연동과 MSA 구조 확장이 필요함
